## 현재 권장 실행 방식

현재 팀 테스트 기준 권장 구조는 아래입니다.

- 프론트: GitHub Pages
- 백엔드: 로컬 FastAPI 서버

이유는 간단합니다.  
현재 백엔드는 `Kiwi + KoBERT + KoBERT-MLM + KoELECTRA + local edit tagger`를 로드하는 무거운 ML 서버라서,
Cloud Run 같은 scale-to-zero 환경보다 **로컬에서 계속 켜두는 방식**이 더 단순하고 안정적입니다.

실행 문서는 여기로 보는 게 맞습니다.

- [docs/backend_api_contract.md](/Users/joh/Desktop/joh9911/MyProject/grammarly_korean/docs/backend_api_contract.md)

```bash
npm run backend:dev
```

새 터미널:

```bash
npm run tunnel:quick
```

공유 링크 생성:

```bash
npm run share:url -- https://fornewchapter.github.io/grammarly_korean_demo/ https://<your-trycloudflare-url>
```

## 현재 저장소 구조

이 저장소는 **repo를 나누지 않는 monorepo 방식**으로 정리되어 있습니다.

- `apps/frontend`
  - Vite/React 프론트엔드
- `apps/backend`
  - FastAPI 백엔드
- `public/assets`
  - 웹/백엔드가 같이 참조하는 정적 자산
- `models`
  - 백엔드 모델 체크포인트
- `scripts`
  - 자산 준비, 실행, 공유 링크 생성 스크립트
- `docs`
  - 팀 운영 문서

기본 공유 링크는 일반 맞춤법 교정기처럼 단순 UI만 보여줍니다.

- 입력
- 검사 버튼
- 제안 문장

상단 상태 패널에서는 현재 붙은 백엔드의 이름 / 브랜치 / 버전을 확인할 수 있습니다.

이 프로젝트는 단순히 문장을 고치는 웹사이트가 아니라,
**온디바이스 한국어 맞춤법 교정이 어떤 단계들을 거쳐 동작하는지 보여주는 데모**입니다.

이 데모를 웹사이트로 만든 이유는 두 가지입니다.

1. Android로 바로 만들면 네이티브 C++ 통합까지 들어가야 해서, 실기기나 에뮬레이터에서만 테스트할 수 있습니다.
2. 웹으로 만들면 접근성이 좋고, 설치 없이도 바로 테스트할 수 있습니다.

즉, 이 저장소의 목적은 아래 두 가지를 보여주는 것입니다.

1. 한국어 맞춤법 교정이 실제로 어떤 단계들을 거쳐 이뤄지는지
2. 이 과정을 로컬 자산과 로컬 추론으로 구현할 수 있는지

## 1. 현재 실행 구조

현재 프로젝트는 두 가지 실행 경로를 가집니다.  
다만 **팀 공유/검증 기준 권장 경로는 로컬 백엔드 + tunnel**이고, 브라우저 정적 경로는 개발/실험용 보조 경로입니다.

### 보조 실행 경로: 브라우저 정적 모드

이 경로는 현재도 남아 있지만, 팀 공유용 주 경로로 권장하지 않습니다.

- Web Worker
- ONNX Runtime Web
- Kiwi wasm
- 정적 JSON 후보 자산
- 브라우저 규칙/후보 생성/랭커

이 경로에서는 아래 기능이 동작합니다.

- 정적 웹 호스팅만으로 실행 가능
- 중앙 API 없이 팀원이 같은 URL에서 테스트 가능
- ONNX 소형 모델 + Kiwi wasm + 자산 기반 후보 생성 사용

정적 사이트 사용 시 실제 흐름은 이렇습니다.

1. 사용자가 사이트에 처음 접속
2. 브라우저가 앱 코드, Kiwi wasm, Kiwi 모델 파일, rules/dict JSON, ONNX 모델을 다운로드
3. 서비스워커 캐시에 저장
4. 이후 새로고침/재방문 시 캐시된 자산 재사용

즉 일반적인 새로고침으로는 자산이 매번 다시 날아가지 않습니다.
다시 다운로드하는 경우는 보통:

- 첫 방문
- 브라우저 캐시/사이트 데이터 삭제
- 새 버전 배포
- 서비스워커 갱신

현재 서비스워커는 `models / kiwi / wasm / onnx`를 `CacheFirst`로 캐시합니다.

정리 문서:
- [docs/static_web_migration.md](/Users/joh/Desktop/joh9911/MyProject/grammarly_korean/docs/static_web_migration.md)

### 대체 실행 경로: 로컬 API 모드

로컬에서 더 무거운 Python 파이프라인을 확인하고 싶다면 API 모드를 강제로 켤 수 있습니다.

- `VITE_PREFER_LOCAL_API=1` 또는 `?localApi=1`
- Python FastAPI 서버
- Kiwi
- KoBERT / KoELECTRA / KoBERT-MLM

즉, 정적 웹 배포는 브라우저 경로가 기본이고, 로컬 API는 비교/개발용 경로입니다.

### 팀 브랜치 협업용 로컬 자산 실행

중앙 서버 비용 없이 팀원이 각자 브랜치에서 같은 런타임을 쓰려면,
모델과 Kiwi 자산을 **각자 로컬 디스크에 준비한 뒤** 브라우저에서 실행하면 됩니다.

중요한 점:

- 원격으로 배포된 정적 사이트는 팀원의 로컬 디스크를 직접 읽을 수 없습니다.
- 대신 각 팀원이 **자기 브랜치에서 로컬로 웹페이지를 띄울 때**, 로컬 자산을 같이 서빙하는 방식은 가능합니다.

#### 표준 경로

- 로컬 모델 원본: `.local-assets/models/`
- 브라우저가 실제로 읽는 경로: `public/assets/models-local/`
- Kiwi 자산 경로: `public/assets/kiwi/model/`

#### 준비 절차

1. 브랜치 체크아웃
2. 실제 ONNX 모델 5개를 `.local-assets/models/`에 넣기
   - `profile_classifier.onnx`
   - `spacing_boundary.onnx`
   - `edit_tagger.onnx`
   - `reranker.onnx`
   - `guardrail.onnx`
3. 아래 실행

```bash
npm install
npm run prepare:runtime
npm run prepare:browser-edit-tagger:local
npm run smoke:browser-edit-tagger
npm run validate:runtime:strict
npm run dev
```

`prepare:runtime`은:

- Kiwi wasm 자산 다운로드
- `.local-assets/models/`의 실모델을 `public/assets/models-local/`로 복사

를 수행합니다.

브라우저에서 실제 transformer edit tagger를 검증하려면 추가로:

- `npm run prepare:browser-edit-tagger:local`
- `npm run smoke:browser-edit-tagger`

를 실행하면 됩니다.

이 경로는 `models/edit_tagger_v2_best/best`에서 브라우저용 ONNX + tokenizer 자산을 생성하고,
샘플 토큰(`아기를`, `나았다`)에 대해 `KEEP`, `OPEN_REPLACE`가 나오는지 확인합니다.

#### 동작 원리

브라우저는 모델을 아래 우선순위로 찾습니다.

1. `/assets/models-local/*.onnx`
2. `/assets/models/*.onnx`
3. 둘 다 실모델이 아니면 heuristic 경로 사용

기본 repo에 들어 있는 `public/assets/models/*.onnx`는 placeholder일 수 있으므로,
실제 팀 테스트에서는 **`models-local`이 잡혀야 정상**입니다.

앱 상단 `AssetStatusPanel`의 model chip은 `ready/local`, `ready/bundled`, `missing`으로 표시됩니다.
팀 브랜치 협업에서는 `ready/local`이 보여야 합니다.

### GitHub Pages 자동 배포

정적 웹 배포용 GitHub Actions가 포함되어 있습니다.

- 워크플로우: [.github/workflows/deploy-static-pages.yml](/Users/joh/Desktop/joh9911/MyProject/grammarly_korean/.github/workflows/deploy-static-pages.yml)
- `main` 브랜치에 푸시하면 `apps/frontend/dist/`를 GitHub Pages로 배포합니다.
- Pages 설정에서 **GitHub Actions**를 배포 소스로 선택하면 됩니다.

프로젝트 페이지 경로를 위해 build 시 `VITE_BASE_PATH=/<repo-name>/`가 자동 적용됩니다.

정적 웹 빌드 전에는 Kiwi wasm 모델 자산을 자동으로 내려받습니다.

- 명령: `npm run prepare:kiwi`
- 내려받는 위치: `public/assets/kiwi/model/`
- 첫 브라우저 실행에서는 `100MB+` 수준의 Kiwi 자산 로딩 때문에 초기 `inspect`가 상대적으로 느릴 수 있습니다.

## 2. 사용한 모델, 엔진, 그리고 역할

이 프로젝트는 여러 모델과 엔진을 나눠서 씁니다.
한 모델이 모든 문제를 한 번에 푸는 구조가 아니라,
각 단계에 맞는 도구를 따로 배치한 구조입니다.

### Python FastAPI 서버

이건 모델이 아니라 전체 파이프라인을 묶어 주는 실행 엔진입니다.

역할:

- 입력을 받음
- 단계별 교정 과정을 순서대로 실행함
- 결과와 trace를 프론트에 전달함

### Kiwi

Kiwi는 한국어 형태소 분석기이자 띄어쓰기 엔진입니다.

역할:

- 띄어쓰기 후보 생성
- 단어를 형태소 단위로 분석
- 기본형과 어미를 바탕으로 자연스러운 후보 표면형 복원
- 문장 전체가 형태상 어색하지 않은지 확인

쉽게 말하면:

- 한국어 단어를 잘게 나눠 보고
- 띄어쓰기와 활용형을 한국어답게 복원하는 역할입니다.

### KoBERT

KoBERT는 한국어 문장을 이해하기 위한 BERT 계열 인코더 모델입니다.

역할:

- 문장 프로파일 분류 보조
- 문장 전체 의미를 벡터로 바꿔 비교

쉽게 말하면:

- 문장의 대략적인 의미와 분위기를 보는 모델입니다.

### KoELECTRA

KoELECTRA는 한국어 문장을 빠르게 판별하는 데 강한 ELECTRA 계열 인코더 모델입니다.

역할:

- 문장 프로파일 분류 보조
- 후보 문장이 원문보다 더 자연스러운지 점수화

쉽게 말하면:

- “이 문장이 더 자연스러운가?”를 판단하는 데 쓰는 모델입니다.

### fine-tuned Edit Tagger

이 모델은 KoELECTRA를 바탕으로 다시 학습한 토큰 분류 모델입니다.

역할:

- 어떤 토큰이 이상한지 찾기
- 그대로 둘지
- 띄어쓰기 쪽으로 보낼지
- 다른 후보를 만들어볼지

를 먼저 판정합니다.

쉽게 말하면:

- 문장 안에서 “수상한 위치”를 먼저 찾는 모델입니다.

### KoBERT-MLM

이 모델은 KoBERT 기반 마스크드 언어 모델입니다.

역할:

- 특정 위치에 어떤 단어가 들어가면 더 자연스러운지 보기
- 교정 후보를 만들거나 후보를 다시 비교할 때 보조 점수로 사용

쉽게 말하면:

- “이 자리에 이 단어를 넣어도 자연스러운가?”를 확인하는 모델입니다.

## 3. 파인튜닝한 모델과 데이터

이 프로젝트에서 실제로 파인튜닝한 모델은
**Edit Tagger**입니다.

### 어떤 모델을 파인튜닝했는가

- 베이스 모델: `monologg/koelectra-base-v3-discriminator`
- 파인튜닝 결과: 한국어 맞춤법 교정용 token classification 모델

즉, 원래의 KoELECTRA를 그대로 쓰는 것이 아니라,
문장 안에서 오류 위치를 찾는 용도로 다시 학습했습니다.

### 어떤 데이터로 학습했는가

사용한 원본 데이터:

- AI Hub `인터페이스(자판-음성)별 고빈도 오류 교정 데이터`

정리된 데이터 규모:

- 학습용 원문-교정문 쌍: `214,300`건
- 검증용 원문-교정문 쌍: `29,050`건

주요 오류 유형:

- 오탈자
- 맞춤법 오류
- 띄어쓰기/문장부호 오류
- 음성 인식 오류
- 자동 생성 오류
- 자주 틀리는 맞춤법 오류

이 데이터로부터 Edit Tagger 학습용 라벨 데이터를 다시 만들었습니다.

현재 저장소에 포함된 1차 모델의 라벨 종류:

- `KEEP`: 그대로 둔다
- `OPEN_REPLACE`: 다른 단어 후보를 만들어본다
- `SPACE_FIX`: 띄어쓰기 체인으로 보내는 편이 낫다
- `PUNCT_FIX`: 애매한 표면 오류로 본다

### 현재 포함된 파인튜닝 모델은 어느 정도 규모로 학습했는가

현재 저장소에 들어 있는 1차 파인튜닝 모델은
Colab에서 아래 조건으로 학습했습니다.

- 학습 데이터: `50,000`문장
- 검증 데이터: `5,000`문장
- epoch: `2`
- batch size: `8`
- gradient accumulation: `4`
- max length: `96`

즉, 전체 준비 데이터는 더 크지만,
현재 포함된 모델은 그중 일부로 먼저 학습한 1차 버전입니다.

이 모델의 목적은
“어떤 토큰을 문맥 교정 후보로 볼지”를 안정적으로 잡는 것입니다.

### 현재 추가로 준비된 v2 학습 경로

현재 저장소에는 Edit Tagger를 다시 학습하기 위한 v2 경로도 같이 들어 있습니다.

v2의 핵심 차이:

- 라벨을 `KEEP / SPACE_FIX / OPEN_REPLACE`로 단순화
- `PUNCT_FIX`를 태거 책임에서 빼고 규칙 단계로 넘김
- 정답 문장 자체를 `KEEP` 예시로 같이 넣어 false positive를 줄임

관련 파일:

- 데이터셋 생성: [scripts/build_edit_tagger_v2_dataset.py](/Users/joh/Desktop/joh9911/MyProject/grammarly_korean/scripts/build_edit_tagger_v2_dataset.py)

프론트 의존성:

## 6. 왜 파이프라인을 단계별로 나눴는가

이 시스템을 한 번에 "문장 하나 넣고 정답 문장 하나를 바로 내는 모델"로 만들 수도 있습니다.
하지만 그렇게 하면 아래 문제가 생깁니다.

- 왜 고쳤는지 설명하기 어렵다
- URL, 숫자, 제품명 같은 보호 구간을 망치기 쉽다
- 띄어쓰기와 문맥 치환이 섞여 과교정이 늘어난다
- 속도 병목이 어디인지 파악하기 어렵다
- 온디바이스 최적화 포인트를 찾기 어렵다

그래서 이 프로젝트는 역할을 분리했습니다.

1. 보호해야 할 것은 먼저 잠근다
2. 쉬운 오류는 규칙과 띄어쓰기 단계에서 먼저 처리한다
3. 문맥이 필요한 오류만 후보 생성과 재정렬 단계로 보낸다
4. 마지막에 정책 단계에서 자동 반영과 제안 여부를 정한다

이렇게 나누면 아래가 명확해집니다.

- 어떤 단계는 규칙 기반인지
- 어떤 단계는 모델 기반인지
- 어떤 단계가 속도 병목인지
- 왜 어떤 수정은 제안만 되는지

## 7. 현재 교정 파이프라인

아래는 현재 구현 기준 실제 단계입니다.

### 1단계. 검사 범위 추출

역할:

- 지금 검사할 문장 범위를 정합니다.

현재 구현:

- `inspect` 모드에서는 입력 전체를 검사합니다.
- 실시간 모드였다면 최근 절만 보도록 설계되어 있습니다.

왜 필요한가:

- 전체 문서를 매번 돌리면 느립니다.
- 온디바이스에서는 검사 범위를 좁히는 것이 중요합니다.

---

### 2단계. 보호 구간 탐지

역할:

- URL
- 이메일
- 전화번호
- 숫자
- 고유명사
- 사용자 사전 항목

같이 **교정하면 안 되는 부분**을 보호합니다.

현재 방법:

- 정규식으로 URL, 이메일, 숫자 같은 패턴을 먼저 찾습니다.
- 도메인 엔티티 목록과 사용자 사전으로 제품명, 고유명사 같은 항목을 보호합니다.

왜 필요한가:

- `https://myshop.co.kr`
- `AirPods Pro 2`

같은 문자열은 맞춤법 모델이 건드리면 신뢰가 바로 무너집니다.

---

### 3단계. 문장 프로파일 분류

역할:

- 일반 문장인지
- 채팅체인지
- 오타가 많은 문장인지
- 영문이나 숫자가 많이 섞였는지

를 판별합니다.

현재 방법:

- 규칙 기반 특징과
- KoBERT, KoELECTRA 임베딩을 함께 봅니다.

쉽게 말하면:

- 규칙은 문장의 겉모습을 빠르게 봅니다.
- 모델은 문장 전체 분위기를 더 넓게 봅니다.
- 이 둘을 합쳐서 `NORMAL`, `CHAT`, `NOISY`, `MIXED`, `QUERY` 중 하나를 고릅니다.

왜 필요한가:

- 같은 수정 후보라도 일반 문장에서는 유용한 교정이 될 수 있고,
- 채팅체에서는 과하게 고친 결과가 될 수 있습니다.

---

### 4단계. 확정 규칙 교정

역할:

- 사전에 있는 확실한 오타를 먼저 고칩니다.

현재 방법:

- 고정된 교정 사전으로 정확한 치환만 먼저 처리합니다.

예:

- `되요 -> 돼요`
- `삿어요 -> 샀어요`

왜 필요한가:

- 이런 오류는 모델까지 보낼 필요가 없습니다.
- 빠르고 정확하게 먼저 처리하는 것이 전체 속도와 안정성에 유리합니다.

---

### 5단계. 띄어쓰기 후보 생성

역할:

- 어디에 띄어쓰기를 넣을 수 있는지 후보를 만듭니다.

현재 방법:

- Kiwi의 띄어쓰기 기능으로 가능한 경계를 먼저 찾습니다.

예:

- 입력: `아기를나았다`
- 후보: `아기를|나았다`

왜 필요한가:

- 한국어 체감 품질에서 띄어쓰기는 매우 중요합니다.
- 띄어쓰기를 먼저 처리하면 뒤 문맥 교정이 더 안정적입니다.

---

### 6단계. 띄어쓰기 후보 판정 / 수정안 생성

역할:

- 띄어쓰기 후보 중 실제로 반영할 것만 남깁니다.
- 그리고 그것을 실제 수정안으로 바꿉니다.

현재 방법:

- 띄어쓰기 후보를 그대로 다 쓰지 않고 한 번 더 걸러냅니다.
- 통과한 후보만 실제 수정안으로 바꿉니다.

예:

- `아기를|나았다 -> 아기를 나았다`

왜 필요한가:

- Kiwi가 만든 모든 후보를 그대로 쓰면 과교정 위험이 있습니다.
- 별도의 판정 단계를 두면 띄어쓰기 처리 경로가 더 명확해집니다.

---

### 7단계. 오류 감지

역할:

- 띄어쓰기 외에 문맥상 이상한 토큰을 찾습니다.

현재 방법:

- fine-tuned KoELECTRA 태거가 각 토큰을 보고
- 그대로 둘지, 다른 후보를 찾아볼지, 띄어쓰기 문제인지 등을 먼저 표시합니다.

여기서 나오는 라벨 예:

- `KEEP`: 그대로 둔다
- `OPEN_REPLACE`: 다른 단어 후보를 만들어본다
- `PUNCT_FIX`: 태거가 애매한 오류로 본다
- `SPACE_FIX`: 띄어쓰기 쪽에서 다시 보는 것이 낫다

왜 필요한가:

- “어디가 이상한지”를 먼저 좁혀야
- 후보 생성과 재정렬을 필요한 토큰에만 적용할 수 있습니다.

---

### 7-1단계. 후속 처리 결정

역할:

- 탐지된 오류를 어떤 체인으로 보낼지 정합니다.

예:

- `SPACE_FIX`는 띄어쓰기 체인으로 보냅니다.
- 애매하지만 후속 후보가 강한 토큰은 문맥 교정 체인으로 승격합니다.

왜 필요한가:

- 탐지와 교정을 분리하면 구조가 복잡하게 엉키지 않습니다.
- 태거 결과를 절대값으로 믿지 않고 후속 신호로 보정할 수 있습니다.

---

### 8단계. 교정 후보 생성

역할:

- 문맥 교정이 필요한 토큰에 대해 실제 교정 후보를 만듭니다.

현재 방법:

- 자주 헷갈리는 교정쌍을 먼저 봅니다.
- 형태 분석을 통해 기본형을 추정합니다.
- 현재 어미를 유지한 채 다른 기본형으로 다시 활용합니다.
- 마지막 보조 수단으로 KoBERT-MLM을 씁니다.

여기서 말하는 기본형이란:

- `낳았다`의 기본형은 `낳다`
- `나았다`의 기본형은 `낫다`
- `좋겠다`의 기본형은 `좋다`

즉, 문장에 나온 표면형을 바로 고치지 않고,
먼저 "이 단어의 원래 형태가 무엇인지"를 보고 후보를 만듭니다.

예:

- `나았다 -> 낳았다`
- `낳앗으면 -> 나았으면`
- `좋겟다 -> 좋겠다`

왜 필요한가:

- 한국어는 활용형이 많아서 단순 문자 치환만으로는 품질이 낮습니다.
- 이 단계가 없으면 `좋겟나`, `막앗으면` 같은 이상한 표면형이 쉽게 올라옵니다.

---

### 8-1단계. 후보 1차 정리

역할:

- 생성된 후보 중 믿을 만한 후보만 남깁니다.

현재 방법:

- 어떤 방식으로 만들어진 후보인지 봅니다.
- 원문과 지나치게 멀어진 후보는 버립니다.
- 형태 복원으로 만든 후보처럼 신뢰도가 높은 후보를 우선 남깁니다.

쉽게 말하면:

- “아무 후보나 다 들고 가지 않고”
- “근거가 더 탄탄한 후보부터 남기는 단계”입니다.

왜 필요한가:

- 이 단계가 없으면 `좋겠다`보다 `좋겟나` 같은 이상한 후보가 앞설 수 있습니다.

---

### 9단계. 문맥 기준 재정렬

역할:

- 남은 후보를 문맥 안에서 다시 비교해 최종 후보를 고릅니다.

현재 방법:

- KoBERT-MLM이 문맥상 어색하지 않은지 보고
- KoELECTRA가 문장 전체가 자연스러운지 보고
- Kiwi가 형태와 띄어쓰기 측면에서 이상하지 않은지 봅니다.

즉, 한 후보를 고를 때 아래 세 가지를 함께 봅니다.

1. 이 위치에 이 단어가 들어가도 자연스러운가
2. 문장 전체가 더 자연스러워졌는가
3. 한국어 형태와 연결이 어색하지 않은가

예:

- `감기 낳앗으면`
  - 형태상 가까운 후보: `낳았으면`
  - 문맥상 더 맞는 후보: `나았으면`

이 차이를 여기서 해결합니다.

왜 필요한가:

- `아기를 나았다 -> 아기를 낳았다`
- `감기 나았다 -> 감기 나았다 유지`

같은 문제는 결국 문맥 판단이 필요합니다.

---

### 10단계. 과교정 방지

역할:

- 후보가 맞아 보여도, 자동 반영이 위험한지 확인합니다.

현재 방법:

- 보호 구간을 건드렸는지
- 숫자나 영문이 손상됐는지
- 의미 치환 위험이 큰지
- 수정 비율이 지나치게 큰지

를 확인합니다.

왜 필요한가:

- 모델이 맞는 후보를 찾았더라도, 자동으로 바꾸는 것이 항상 안전한 것은 아닙니다.

---

### 11단계. 적용 정책 결정

역할:

- 자동 반영
- 제안만
- 차단

중 무엇으로 처리할지 정합니다.

현재 정책:

- 띄어쓰기와 확정 철자 규칙은 자동 반영 가능
- 문맥형 단어 치환은 기본적으로 제안만

왜 필요한가:

- 탐지 품질이 높더라도 모든 문맥 치환을 자동 반영하면 과교정 위험이 있습니다.

---

### 12단계. 최종 결과 정리

역할:

- 현재 결과 문장
- 제안 수
- 자동 반영 수
- 차단 수

를 정리해서 화면에 전달합니다.

## 9. 현재 구조의 핵심 논리

이 프로젝트는 아래 철학으로 동작합니다.

### 1. 쉬운 문제는 먼저 처리한다

- 규칙 교정
- 띄어쓰기

이 두 경로를 먼저 처리하면 뒤 단계가 더 적은 span만 보게 됩니다.

### 2. 문맥형 문제는 분리한다

문맥이 필요한 문제는 아래처럼 분리합니다.

- 탐지
- 후보 생성
- 후보 1차 정리
- 재정렬

이렇게 해야 특정 문장 예외처리가 계속 쌓이지 않습니다.

### 3. 겉보기에는 둘 다 맞는 문제를 별도로 다룬다

`나았다`와 `낳았다`처럼 둘 다 표면형이 가능해 보이는 문제는
오타 수정이 아니라 문맥 선택 문제입니다.

이 경우에는:

- 기본형 기준 후보 생성
- 문맥 기반 재정렬

이 핵심입니다.

### 4. 정책은 마지막에 분리한다

모델이 맞는 후보를 찾았더라도,
자동으로 바꿀지 여부는 별도 문제입니다.

그래서 후보 품질과 제품 정책을 분리해서 생각할 수 있도록 마지막 정책 단계를 둡니다.

## 10. 현재 병목과 개선 포인트

현재 가장 큰 병목은:

- 문장 프로파일 분류
- 오류 감지
- 후보 재정렬

특히 문맥형 후보가 많아질수록 후보 재정렬 비용이 커집니다.

현재까지 적용한 구조 개선:

- 오류 감지 단계에서 무거운 재점수화를 제거
- 후보 생성과 재정렬 분리
- 후보 1차 정리 단계 추가
- 신뢰도가 높은 후보를 우선하는 구조 추가

이 덕분에 구조는 이전보다 훨씬 깔끔해졌습니다.

남은 과제:

- 브라우저 경로와 로컬 API 품질 차이 줄이기
- ONNX 경로 통합
- 문맥형 제안의 자동 반영 정책 정교화
